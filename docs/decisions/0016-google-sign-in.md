# 0016 — Google sign-in

- **Status:** Accepted
- **Date:** 2026-10-13 (Google sign-in stage, between B6 and B7)
- **Decided by:** Owner (build it now; items 4 and 7, approved in the plan). Claude Code (the rest). Owner may revisit any item.

## Decisions

1. **Backend authorisation-code flow with PKCE, `state` and `nonce`** (backend.md §4). The browser goes to `GET /auth/google/start`. The API creates a one-time `state`, a PKCE verifier (S256) and a `nonce`, keeps them in Redis for `GOOGLE_FLOW_TTL_MIN` (10) minutes, and redirects to Google. Google returns the browser to `GET /auth/google/callback`. The API swaps the code for an ID token server-side with the client secret, so no token passes through the browser. It then checks the token's signature against Google's published keys (cached for an hour; an unknown key ID refetches once), plus its audience, issuer, expiry (60 s leeway) and nonce. Google's endpoints are reached through a small `httpx` client (`app/integrations/google.py`), the same choice as Paystack and Firestore (ADR 0014). It adds no new dependency.
2. **Login CSRF protection: `state` is bound to the browser.** `start` sets the `state` in an httpOnly, `SameSite=Lax` cookie (`hv_google_state`, path `/api/v1/auth/google`). The callback requires the cookie to equal the `state` in the URL, then spends the Redis entry (`GETDEL`), so each state works once. An attacker's own code and state replayed in a victim's browser fails, because the victim has no matching cookie. Redis keys are SHA-256 hashes of the random values.
3. **Account matching** (backend.md §4). Only identities whose email Google marks `email_verified: true` (exactly `true`) are used; otherwise `google_error=email_not_verified`. Match by `google_sub` first, then by email (case-insensitive, `citext`). If that email's account is already linked to a *different* Google account, it is refused (`other_google_account`). Suspended accounts are refused whichever way they match (`suspended`). Sign-in updates `last_login_at`, as a password login does.
4. **Linking to an account whose email was never verified removes its password** (owner, in the plan). Anyone can sign up with an address they don't own and never verify it. Linking would then share the account with that person. So linking such an account also marks the email verified, clears `password_hash`, revokes every refresh token, and spends any open verify or reset links. Its owner can set a password later through "Forgot password". A verified account just gains the link and keeps its password. Unverified accounts can't have registered an agency or posted requests (both need a verified email), so nothing of value is lost.
5. **New Google users choose family or agency before an account exists** (backend.md §4, ADR 0011 item 1). The callback stores the Google identity in Redis for `GOOGLE_PENDING_TTL_MIN` (15) minutes behind a second httpOnly cookie (`hv_google_pending`). It then redirects to the web app's `/signup/google`, which reads `GET /auth/google/pending` and posts `POST /auth/google/complete {full_name, role, privacy_notice_version}`. The account is created with the email verified, no password, the `google_sub` and the privacy-notice version, and is signed in like a login (access token plus refresh cookie). The pending entry is spent once (`GETDEL`). New agency admins go straight to agency onboarding. The name is asked for (pre-filled from Google), because Google may not supply one.
6. **The session reaches the web app through the existing refresh cookie.** On success the callback sets `hv_refresh` exactly as login does, and redirects to `/login?google=signed_in&next=…`. The login screen restores the session (refresh, then `/me`) and follows `next` through the web app's existing open-redirect guard (`redirects.ts`). The API also drops anything that isn't a same-site path before storing it. No token ever appears in a URL.
7. **Errors are redirects, not JSON** (owner, in the plan). `start` and `callback` are browser navigations, so every failure goes to `/login?google_error=<code>`, which the login screen explains. The codes are `unavailable` (Google settings not set), `rate_limited`, `cancelled` (Google's `access_denied`), `expired` (bad or missing state cookie, or a spent or expired state), `failed` (Google refused the code, or the token didn't check out), `email_not_verified`, `suspended` and `other_google_account`. They are display codes for the web app only, not new API error codes. `pending` and `complete` use the existing envelope: 410 `TOKEN_EXPIRED` when there is no pending sign-up, 409 `EMAIL_TAKEN`, 422 `VALIDATION_ERROR`, and 403 `FORBIDDEN` from the Origin check (ADR 0011 item 5).
8. **Additions to the frozen contract (ADR 0009):** `GET /auth/google/pending` and `POST /auth/google/complete`, plus the documented behaviour of `start` (optional `next`) and `callback`. No existing endpoint changes. The web app gains the `/signup/google` route.
9. **Settings:** `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` must both be set, or neither, and the app refuses to start otherwise. With neither set, Google sign-in is off and the button lands on the "unavailable" message. The redirect URI is derived as `API_BASE_URL + /api/v1/auth/google/callback` and must be registered in the Google Cloud console exactly. Tests pin a fake client in `TEST_ENV`, so the owner's real client in `.env` is never used by tests.
10. **Rate limit:** `start` is limited per IP with `RATE_LIMIT_AUTH_PER_MIN` (scope `google`). The callback needs an unspent state from `start`, so `start`'s limit also caps callbacks, and `complete` needs a pending sign-up from the callback.
11. **Logging:** codes, ID tokens, the client secret, cookies and emails are never logged. A failed sign-in logs `google.sign_in_failed` with a short reason (for example `nonce mismatch` or `InvalidAudienceError`). A link logs `user.google_linked` with the user ID and whether the password was removed.

## Consequences

- No migration: `users.google_sub` (unique) and the nullable `password_hash` have existed since migration 0002.
- `scripts/google_live_check.py` checks the client ID and secret against Google without a browser, by sending a made-up code and expecting `invalid_grant`. The full browser round trip is checked by hand with mocks off. It belongs with B7 (web app connected to the API).
- In demo mode (MSW) the Google button still only shows its notice. The mock implements `pending` and `complete` with the same rules, for tests.
- Production (B8): register `https://<api domain>/api/v1/auth/google/callback`, publish the OAuth consent screen (it stays in "testing" mode until then, and only listed test users can sign in), and serve the web app and API on the same site (ADR 0011 item 10).
- Not done: emailing the owner when Google is linked to an existing account, and unlinking Google from settings. Both are candidates for later.
